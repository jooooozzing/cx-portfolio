Case 03

찾지 않아도 닿는 지식

Problem
스크립트와 정책이 여러 문서에 흩어져 같은 질문에 다른 답이 나갔고, AI가 참조할 수 있는 형태도 아니었습니다
Insight
분류 체계를 먼저 만들고 발화를 끼워 넣는 방식은 쓰지 않았습니다. 실제 발화에서 분류가 나와야, 실제 문의가 그 분류에 들어맞습니다
Structure
마스터 DB 통합 → 실제 상담 발화 클러스터링 → 문의 단계별 지식 블록 재구성 → Databricks 기반 내부 챗봇 → L1~L4 고도화 로드맵

Stakeholders

읽기

같은 질문에 다른 답이 나갔습니다.
기준이 없어서가 아니라, 기준이 여러 문서에 나뉘어 있었기 때문입니다.

현장에서 반복된 상황

같은 문의인데 참조한 문서가 다르면 답이 달라집니다

어느 문서가 최신인지 확인하는 데 시간이 듭니다

문서를 한곳에 모으는 것으로는 풀리지 않는 문제였습니다.
모아두어도, 사람이 그 안에서 맞는 조각을 찾아야 하는 구조는 그대로이기 때문입니다.

실제 문제

① 문서가 사람 기준으로 정리돼 있었습니다
— 부서별 · 시기별 · 파일별. 읽는 사람은 맥락을 알지만, 기계는 모릅니다

② 참조되려면 질문 단위로 쪼개져 있어야 합니다
— "교환 정책 문서"가 아니라 "이 질문에는 이 근거로 이렇게 답한다"의 단위

그래서 목표를 다시 잡았습니다.
문서를 정리하는 것이 아니라, 참조 가능한 단위로 지식을 다시 쓰는 것.

실행
01
마스터 DB 통합 — 904행 (v3.1)
  • 여러 문서에 흩어져 있던 스크립트와 정책을 하나의 마스터 DB로 통합. 현재 904행, 버전 v3.1로 관리
  • 반복해서 쓰이는 문장은 표준문장 S-01~S-08로 분리해, 개별 답변이 아니라 공통 블록을 참조하도록 구성
  • 표준문장은 4개국어로 관리해, 언어가 달라도 같은 근거를 참조하도록 했습니다
02
실제 상담 발화 클러스터링 — 약 102건 → 7개 패턴 → 6개 그룹
  • 기획 문서가 아니라 실제 상담에서 오간 발화 약 102건을 수집해 출발점으로 삼았습니다
  • 표현을 7개 패턴으로 묶고, 패턴을 다시 6개 그룹으로 정리. 고객이 실제로 쓰는 말이 분류의 기준이 되도록 했습니다
  • 분류 체계를 먼저 만들고 발화를 끼워 넣는 방식은 쓰지 않았습니다. 그 경우 실제 문의가 분류에 안 맞는 일이 반복됩니다
03
문의 단계별 지식 블록 재구성 — 상담 DB 109행 · 질문 DB 102행
  • 클러스터링 결과를 문의가 진행되는 단계에 따라 다시 배치. 같은 주제라도 첫 문의와 재문의는 필요한 근거가 다릅니다
  • 상담 DB 109행(응대 단위)과 질문 DB 102행(질의 단위)으로 나눠, 질문에서 근거를 찾아가는 경로를 만들었습니다
04
Databricks 기반 내부 챗봇 개발
  • 재구성한 지식 블록을 참조하는 내부용 챗봇을 개발. 상담사가 정책 근거를 찾는 시간을 줄이는 것이 1차 목적입니다
  • 현재 기본 질의응답 동작을 확인한 단계이며, 배포 전입니다
지식이 다시 쓰인 경로
흩어진 문서 → 통합 마스터 DB → 실제 발화 기반 재구성 → 참조 가능한 블록

선행 작업 — 같은 원리로 먼저 했던 것

이 구조는 처음 시도한 방식이 아닙니다.
향 추천 AI 데이터셋을 설계할 때, 고객이 쓰는 표현과 내부 용어를 잇는 매핑 구조를 먼저 만들었습니다. 고객은 내부 분류명으로 말하지 않기 때문에, 표현과 용어를 연결해 두지 않으면 어떤 추천도 성립하지 않습니다. SKU 183행을 기준으로 이 매핑을 구성했고, 고객 언어를 입구로 두고 내부 지식을 연결한다는 점에서 지금의 지식 블록 구조와 같은 원리였습니다.

영문 CS 응대 워크플로우도 같은 흐름에 있습니다. 응대 판단 기준과 카테고리별 금칙어를 명문화해 AI 워크플로우에 내장했고, 개인의 어학 역량이 아니라 프롬프트에 담긴 기준이 답변 품질을 담보하도록 했습니다.

로드맵 — L1~L4 고도화 단계 정의

챗봇은 배포 전 단계이며, 운영 지표는 아직 없습니다.

정성

지식을 모으는 일과 기계가 읽을 수 있게 만드는 일은 다릅니다.
전자는 보관의 문제이고, 후자는 구조의 문제입니다.

분류를 먼저 정하지 않고 실제 발화에서 끌어낸 것이 이 작업의 판단이었습니다.
기획자가 예상한 질문이 아니라, 고객이 실제로 한 질문이 지식의 입구가 됩니다.

같은 질문에 같은 근거로 답하려면, 그 근거가 먼저 참조 가능한 형태여야 합니다.

확장 — L1~L4 고도화 로드맵
L1 기본 질의응답

→ 정리된 지식 블록을 참조해 답을 반환하는 단계. 현재 동작을 확인한 지점입니다.

L2 문맥 기반 응답

→ 문의 단계와 이전 대화를 반영해 같은 주제에서도 다른 근거를 고르는 단계.

L3 정책 판단 지원

→ 답변 제시에서 나아가, 어떤 정책 조항이 적용되는지와 적용 상태를 함께 제시하는 단계.

L4 지식 갱신 루프

→ 응대에서 드러난 공백이 다시 지식 블록으로 반영되는 단계. 여기까지 가야 사람이 문서를 손보지 않아도 지식이 유지됩니다.

현재는 L1을 확인한 상태이며, 배포 전입니다.
단계를 미리 나눠 둔 이유는, 어디까지 왔는지를 매번 다시 설명하지 않기 위해서입니다.
